AI Clinic Voice Receptionist – Build & Deployment Guide

Version 2 · 11 November 2026 · Updated from version 1 (7 November 2026) with what was actually built, how it was tested, what was measured, and what changes for production.

Client location: Calgary, Alberta, Canada. Development and testing: India. Production deployment: Canada (AWS ca-west-1, Calgary).

Model: one dedicated agent per clinic (single-tenant). Shared core codebase, separate config and deployment per clinic.

All prices are approximate and in USD. Vendor prices and free tiers change often, so check each vendor's pricing page before you quote a client.

What changed since version 1

  • Phase 0 and Phase 1 are built and tested. The whole system (agent, backend, database, staff dashboard) runs on one laptop and has handled real browser calls through LiveKit, including a call by the developer in the LiveKit Playground on 11 Nov 2026.
  • Development runs on local, free components: Qwen3 8B on Ollama for the LLM and self-hosted Kokoro for the voice. No patient data and no test audio leave the laptop for those two legs. Cartesia stays the production voice; switching is one line in clinic.yaml.
  • Timed tests use Groq (Qwen 3.8 27B). The best measured run: 1.21 s median from the end of the caller's sentence to the first sound of the reply, under the 1.5 s target.
  • Safety rules are enforced in code, not only in the prompt: emergency (911) and crisis (988) detection before the LLM, a medical-advice filter on every reply, and a read-back check before any booking.
  • Correction: v1 gave the latency target as "about 1 second" in one place. The target used throughout is under 1.5 s median per reply.
  • New sections: how it was tested (§6), latency results and tuning (§7), and what changes for production (§8).

1. What the system does

A patient calls the clinic's Calgary phone number. The AI answers, understands what they say, replies in a natural voice and can:

  • Answer FAQs (hours, location, services, parking, insurance), using only what is in the clinic's config file
  • Take booking, rescheduling and cancellation requests (staff confirm them in the dashboard until the clinic's booking system is connected)
  • Take messages for the front desk
  • Transfer urgent or clinical calls to a human, or tell callers to hang up and dial 911 in an emergency (988 for a mental-health crisis)

Every call is saved with its transcript, a short summary and any request, and appears on the staff dashboard within about a second of hang-up.

3. Architecture: how each part talks to the next

Call flow, step by step (unchanged from v1, with the latency target corrected):

  1. Patient → Twilio: the patient dials the clinic's Calgary number (PSTN).
  2. Twilio → LiveKit: Twilio forwards the call over SIP. LiveKit creates a room and adds the caller.
  3. LiveKit → agent: LiveKit dispatches the Python agent into the room. Audio streams both ways over WebRTC.
  4. Agent → Deepgram: caller audio goes over a WebSocket; live text comes back.
  5. Agent → guardrails → LLM: every caller message is screened for emergency and crisis language first. A match plays a fixed 911 or 988 message and never reaches the LLM. Otherwise the text, the conversation history and the clinic's system prompt go to the LLM (OpenAI-compatible API, streaming).
  6. LLM → tools: to check a slot, book, cancel, take a message or transfer, the LLM emits a tool call. The agent validates it and calls the FastAPI backend, which talks to the booking system and database.
  7. LLM → advice filter → TTS: each sentence of the reply is checked for medical advice before it is spoken, then streamed to the TTS.
  8. Agent → LiveKit → Twilio → patient: audio plays to the caller. Target: under 1.5 s median from the end of the caller's sentence to the first sound of the reply.
  9. After the call: transcript, summary and any request are saved to PostgreSQL and pushed to the dashboard; urgent calls trigger a staff alert.
Patient phone → Twilio (PSTN) → SIP trunk → LiveKit room → Python agent → [Deepgram STT → guardrails → LLM (Qwen) → advice filter → TTS] → LiveKit → Twilio → patient
Side channel: LLM tool call → FastAPI backend → booking system / email / SMS / PostgreSQL → dashboard (WebSocket)

Two paths, kept separate: the voice loop never waits on the database. Call records are written in the background; tool calls are the only backend requests made while the caller waits, and they have short timeouts. If the backend is down, messages are kept on disk and replayed later.

4. Single-tenant setup (one agent per clinic)

  • One core Git repository. Each clinic is a folder: clinics/<clinic>/clinic.yaml (name, hours, services, FAQs, transfer number, voice, greeting, limits; committed) and clinics/<clinic>/.env (keys; never committed).
  • Nothing clinic-specific is written in the code. Adding a clinic means copying the folder and setting CLINIC=<folder>; a test proves a second clinic runs with no code change.
  • clinic.yaml is checked when the agent starts, not mid-call: it won't load unless the greeting mentions AI and recording.
  • Each clinic gets its own deployment: separate container set, Twilio number, LiveKit dispatch rule and database. Bug fixes go into the core repo once, then each clinic is redeployed.

Step 1 – Accounts

LiveKit Cloud (free tier), Deepgram (free credit), Cartesia (free tier; its free credit ran out during testing), Groq (free tier, no card), OpenRouter (optional; its free tier is capped at 50 requests a day until $10 of credit is bought). Twilio is only needed from Phase 2. Every key is checked at startup and with python -m core.check_env --live, which calls each vendor to prove the key works.

Step 2 – Local stack

  • Python 3.11+, Node.js 20+, Docker Desktop, Git, Ollama.
  • docker compose -f deploy/docker-compose.yml --profile agent up -d --build starts Postgres, backend, dashboard, the voice agent and Kokoro. The GPU override file runs Kokoro on the NVIDIA GPU.
  • The agent runs in Docker, not natively, because Windows Smart App Control blocks LiveKit's native library. Do not switch Smart App Control off for this.
  • Tested in the browser with the LiveKit Agents Playground: no phone number needed, free.

Step 3 – The LLM (Qwen)

  • Local: ollama pull qwen3:8b, then ollama create qwen3-clinic -f Modelfile.qwen3. The Modelfile sets an 8k context (Ollama's default 2k cuts off the system prompt) and a low temperature.
  • Lessons from testing:
    • Ollama ignores Qwen3's /no_think. Send {"reasoning_effort": "none"} or every reply "thinks" for 2–6 s.
    • On Windows use 127.0.0.1, not localhost: localhost tries IPv6 first and added about 2 s per request.
    • Qwen3 8B passed 22/22 text scenarios and 8/8 multi-step runs; Qwen 2.5 7B finished multi-step flows only 4 times in 8. Qwen3 8B is the local default.
    • The agent has the LLM read the system prompt while the greeting plays (a "warm-up"), cutting the first reply's LLM time from 1.6 s to 0.12–0.5 s on Ollama. Turned off on Groq, where it only uses up the rate limit.
    • A stalled LLM request is abandoned after 4 s and retried at once. If the LLM fails for good, the caller hears an apology and the clinic's number, never silence.
  • Groq: same settings with Groq's URL, key and qwen/qwen3.8-27b. Fast, but the free tier allows only about 7,000 input tokens per minute (see §11).

Step 4 – Tools and guardrails

Five tools, each calling the FastAPI backend: check_availability, book_appointment, cancel_appointment, take_message, transfer_to_human. Built-in protections:

  • Every tool payload is validated; on the first error the LLM gets a correction, on the second it is told to take a message instead.
  • Read-back in code: booking, cancelling and messages are refused until the agent has read the phone number (and date and time) back and the caller has said yes. Small models get digits wrong; this stops a wrong number being saved.
  • While a tool runs, the agent says a short line ("Let me check that for you") if it hasn't already said something, so the caller doesn't sit in silence.
  • If the agent promises a callback but nothing was saved, the call is flagged "Needs action" on the dashboard.
  • Limits from clinic.yaml: re-prompt after silence, then hang up; maximum turns; maximum call length.

Step 5 – Booking

The manual adapter ships first: availability comes from the clinic's hours, the request is recorded and staff confirm it from the dashboard. The clinic's own system (Jane App, Google Calendar, Accuro, Oscar or Cliniko) plugs in behind the same interface once they name it. If it's Jane App, apply for API access early: it is limited.

Step 6 – Voice (TTS)

Development uses self-hosted Kokoro (Kokoro-FastAPI, voice af_heart), so testing costs nothing and no text leaves the machine. On the RTX 5050 (a Blackwell GPU) the upstream GPU image fails ("no kernel image is available"); deploy/Dockerfile.kokoro-gpu swaps in a CUDA 12.8 PyTorch build. Production uses Cartesia by changing tts_provider: cartesia and the voice ID in clinic.yaml; the Cartesia code path is kept live and unchanged.

Step 7 – Real phone number (Phase 2, next)

  1. Buy a Calgary number in Twilio (403, 587 or 825).
  2. Create an Elastic SIP trunk; set its origination URI to the LiveKit SIP URI; attach the number.
  3. In LiveKit, create an inbound SIP trunk and a dispatch rule that puts callers in a room with the agent.
  4. The agent already reads the caller's number from the SIP From header; verify it on real calls.
  5. Test from India with a SIP softphone (Zoiper) or Twilio Voice in the browser to avoid international charges.

Step 8 – Deploy to Canada (Phase 5)

See §8 for the full list of production changes.

Where the time goes on the best run (per reply): end-of-speech wait 0.42–0.48 s, speech-to-text 0.24–0.47 s, LLM first token 0.38–0.45 s, Kokoro first audio 0.10–0.19 s (Cartesia measured 0.13–0.17 s).

What was tuned:

  • End-of-turn silence (voice.end_of_turn_silence in clinic.yaml): how long the caller must be silent before the agent answers. Silero's built-in 0.55 s was the real floor, so lowering LiveKit's delay alone did nothing; both are now set from this one value. The demo clinic uses 0.4 s. Lower is faster but can cut in when a caller pauses while reading out a number; re-tune on real phone calls.
  • Prompt warm-up during the greeting (first reply 1.6 s → 0.12–0.5 s on Ollama).
  • Qwen3 "thinking" off; 127.0.0.1 instead of localhost on Windows.
  • A spoken hold-on line during tool calls (booking turns took 4–6 s on local models).
  • LLM request timeout 4 s with an immediate retry (a real call once stalled 19 s).

Must be re-done or re-measured in production

  • Latency on real phone calls with the production LLM and Cartesia: the phone network adds delay that browser tests don't show. Target still under 1.5 s median.
  • End-of-turn silence on real phone audio and real callers, especially older callers and anyone reading out a number.
  • Emergency and no-advice checks by voice after every prompt change.
  • Interrupting: stop time measured 0.5–2.2 s across runs (limit 1.5 s); recheck on the phone path.

Known gaps today

  • TTS failure leaves the caller in silence (Phase 4 fallback above).
  • The answer to "what services do you offer" is weak; the prompt should list services from clinic.yaml.
  • The hold-on line and the 0.4 s end-of-turn setting are covered by automated tests but have little live-call history yet.

9. Privacy and compliance (Alberta)

  • Alberta Health Information Act (HIA) applies to health information handled by custodians such as clinics. The clinic is the custodian; you are their affiliate or service provider. PIPEDA / PIPA (Alberta) may also apply.
  • During development: fake patient data only. With Ollama and Kokoro the LLM and voice legs stay on the laptop; Deepgram, LiveKit and Groq still process test audio or text in the US.
  • Before go-live (non-negotiable): cloud voice APIs send patient audio and transcripts outside Canada, so the clinic must accept that explicitly and in writing, with DPAs signed and the clinic's Privacy Impact Assessment signed off by their privacy officer.

12. Database and staff dashboard

Tables built (PostgreSQL, Alembic migrations): calls (caller, times, reason, urgency, outcome, summary, transcript, per-reply latency, status), appointment_requests, messages, staff_users, audit_log (every staff read and write of a patient record). Without it, messages vanish when the call ends and there is no record for staff or audits. In production: RDS in ca-west-1, encrypted.

Dashboard built: staff login with session cookies; call list newest first with New / Urgent / Today filters and search; call detail with summary, transcript and requested appointment; mark handled, add a note, assign; live updates over WebSocket with a sound. For production: HTTPS, optional two-factor sign-in, and alerts by email or SMS ("New urgent call, check the dashboard", no patient details).
